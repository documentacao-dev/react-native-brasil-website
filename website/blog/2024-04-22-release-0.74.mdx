Hoje estamos lançando o React Native 0.74! Esta versão adiciona Yoga 3.0, Bridgeless por padrão na New Architecture, atualizações de `onLayout` em lote (New Architecture) e Yarn 3 como gerenciador de pacotes padrão para novos projetos.

Também estamos removendo APIs descontinuadas, com a remoção de `PropTypes` e mudanças incompatíveis no `PushNotificationIOS`. No Android, SDK 23 (Android 6.0) é agora a versão mínima suportada.

## Destaques {#highlights}

### Yoga 3.0

#### Novos Comportamentos de Layout {#new-layout-behaviors}

O React Native 0.74 inclui [Yoga 3.0](https://yogalayout.dev/blog/announcing-yoga-3.0), a versão mais recente do nosso mecanismo de layout. O Yoga 3.0 melhora o layout tornando a estilização mais previsível e suporta a renderização de componentes escritos para a web.

O React Native continua a preservar intencionalmente alguns comportamentos incorretos de layout, onde corrigi-los afetaria um número significativo de componentes do mundo real. A conformidade de layout poderá ser configurada de forma mais granular em versões futuras do React Native.

:::warning

O React Native [anteriormente invertia](https://yogalayout.dev/blog/announcing-yoga-3.0#correct-handling-of-logical-edges-in-row-reverse-containers) as bordas `left`/`right` (e `start`/`end`) ao lidar com `margin`, `padding` ou `border`, definidos em um container `row-reverse`. Agora, o comportamento dessas propriedades se alinha com a web. Código que anteriormente dependia de bordas invertidas pode precisar ser atualizado para continuar renderizando corretamente.

#### Suporte para `align-content: 'space-evenly'` {#support-for-align-content-space-evenly}

#### Suporte para `position: 'static'` {#support-for-position-static}

:::info
`position: 'static'` é suportado apenas na New Architecture.
:::

Elementos marcados como [`position: 'static'`](https://developer.mozilla.org/en-US/docs/Web/CSS/position#static) não podem ser deslocados e não são considerados ao determinar o [bloco contêiner](https://developer.mozilla.org/en-US/docs/Web/CSS/Containing_block) de um elemento posicionado absolutamente. Isso permite posicionar um elemento relativo a um ancestral que não é seu pai direto.

### New Architecture: Bridgeless por Padrão {#new-architecture-bridgeless-by-default}

Nesta versão, estamos tornando o Bridgeless Mode o padrão quando a New Architecture está habilitada. Você pode aprender mais sobre nossa mudança para Bridgeless como padrão em [este post](https://github.com/reactwg/react-native-new-architecture/discussions/174). Para tornar a transição mais suave, aprimoramos as camadas de interoperabilidade para cobrir Bridgeless e trabalhamos com várias bibliotecas para garantir que funcionarão em Bridgeless desde o primeiro dia.

Bridgeless não é a única camada de interoperabilidade em que trabalhamos: melhoramos as camadas de interoperabilidade do New Renderer também. A parte mais empolgante é que agora está habilitada por padrão: você não precisa especificar os componentes que devem passar por ela! Você pode ler mais sobre elas [aqui](https://github.com/reactwg/react-native-new-architecture/discussions/175).

Finalmente, se você quiser aprender mais sobre a New Architecture, pode encontrar documentação no repositório [react-native-new-architecture](https://github.com/reactwg/react-native-new-architecture/tree/main/docs). Quando a New Architecture se tornar o padrão, essas informações serão incorporadas ao [reactnative.dev](https://reactnative.dev).

### New Architecture: Atualizações de `onLayout` em Lote {#new-architecture-batched-onlayout-updates}

Atualizações de state em callbacks `onLayout` agora são processadas em lote. Anteriormente, cada atualização de state no evento `onLayout` resultaria em um novo commit de renderização.

```jsx
function MyComponent(props) {
  const [state1, setState1] = useState(false);
  const [state2, setState2] = useState(false);

  return (
    <View>
      <View
        onLayout={() => {
          setState1(true);
       }}>
      <View
         onLayout={() => {
          // When this event is executed, state1's new value is no longer observable here.
          setState2(true);
        }}>
      </View>
    </View>
  );
}
```

Na versão 0.74, as atualizações de `setState1` e `setState2` são processadas em lote juntas. Esta mudança é o [comportamento esperado no React](https://react.dev/learn/queueing-a-series-of-state-updates#react-batches-state-updates) e permite menos re-renderizações.

:::danger
Esta mudança **pode quebrar código** que dependia de atualizações de state não processadas em lote. Você precisará refatorar este código para usar [funções atualizadoras](https://react.dev/learn/queueing-a-series-of-state-updates#updating-the-same-state-multiple-times-before-the-next-render) ou equivalente.
:::

### Yarn 3 para Novos Projetos {#yarn-3-for-new-projects}

[Yarn 3](https://yarnpkg.com/blog/release/3.0) agora é o gerenciador de pacotes JavaScript padrão para novos projetos inicializados com React Native Community CLI.

O Yarn 3.x será usado com `nodeLinker: node-modules`, um modo que fornece compatibilidade com bibliotecas React Native. Isso substitui o Yarn Classic (1.x, descontinuado) como padrão anterior. Para atualizar a versão do Yarn dentro do seu aplicativo existente, você pode seguir este [guia](https://yarnpkg.com/migration/guide).

```sh
$ yarn --help
━━━ Yarn Package Manager - 3.6.4 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  $ yarn <command>
```

O Community CLI também suporta a inicialização de projetos com outros gerenciadores de pacotes via flag `--pm` ([leia mais](https://github.com/react-native-community/cli/blob/main/docs/init.md)).

## Mudanças Incompatíveis {#breaking-changes}

### Aumento do SDK Mínimo do Android (Android 6.0) {#android-minimum-sdk-bump-android-60}

O React Native 0.74 tem um requisito de versão mínima do Android SDK de 23 (Android 6.0). Anteriormente, era Android 5.0 (API 21). Veja nosso contexto para esta mudança [aqui](https://github.com/react-native-community/discussions-and-proposals/discussions/740).

#### Bônus: Redução do tamanho do aplicativo Android {#bonus-android-app-size-reduction}

O aumento do SDK mínimo, juntamente com várias melhorias em nossa build nativa, nos permitiu reduzir bastante o tamanho do aplicativo nos dispositivos dos usuários.

Por exemplo, um aplicativo recém-criado com React Native 0.74 ocupa ~13% menos espaço no dispositivo do usuário, resultando em ~4MB economizados no dispositivo.

![Comparação lado a lado de um novo aplicativo React Native na visualização de armazenamento do sistema Android](/blog/assets/0.74-android-app-size.jpg)

### Remoção de `PropTypes` Descontinuados {#removal-of-deprecated-proptypes}

Antes da versão 0.74, o React Native continuava a incluir `PropTypes`, uma API que foi descontinuada desde o React 15.5 em 2017! Agora estamos removendo todos os `PropTypes` integrados do React Native, reduzindo o tamanho do aplicativo (26.4kB em um bundle minificado) e a sobrecarga de memória.

As seguintes propriedades `PropTypes` foram removidas: `Image.propTypes`, `Text.propTypes`, `TextInput.propTypes`, `ColorPropType`, `EdgeInsetsPropType`, `PointPropType`, `ViewPropTypes` (veja [commit](https://github.com/facebook/react-native/commit/228cb80af9ded20107f3c7a30ffe00e24471bfeb)).

Se seu aplicativo ou biblioteca depende de `PropTypes`, recomendamos fortemente migrar para um sistema de tipos como TypeScript.

### Mudanças na API do PushNotificationIOS (Descontinuado) {#api-changes-to-pushnotificationios-deprecated}

No React Native 0.74, estamos tomando medidas para remover a biblioteca descontinuada [PushNotificationIOS](https://reactnative.dev/docs/pushnotificationios). As mudanças nesta versão estão focadas em remover referências a APIs antigas do iOS. O PushNotificationIOS foi migrado para o framework [User Notifications](https://developer.apple.com/documentation/usernotifications?language=objc) da Apple e expõe novas APIs para agendar e lidar com notificações.

Na próxima versão (0.75), estamos planejando **remover esta biblioteca**, realocando-a para fora do core do React Native e para o pacote da comunidade, [@react-native-community/push-notification-ios](https://github.com/react-native-push-notification/ios). Se você ainda depende do PushNotificationIOS, precisará migrar antes da próxima versão.

#### Mudanças na API {#api-changes}

O callback `didRegisterUserNotificationSettings:` no `RCTPushNotificationManager` era um no-op e foi excluído.

Os seguintes callbacks no `RCTPushNotificationManager` foram descontinuados e serão removidos na versão 0.75:

```objectivec
+ (void)didReceiveLocalNotification:(UILocalNotification *)notification;
+ (void)didReceiveRemoteNotification:(NSDictionary *)notification;
```

Para recuperar a notificação que iniciou o aplicativo usando `getInitialNotification()`, agora você precisará definir explicitamente a `initialNotification` no `RCTPushNotificationManager`:

```objectivec
[RCTPushNotificationManager setInitialNotification:response.notification];
```

No lado JS, as propriedades em `Notification` foram alteradas. `alertAction` e `repeatInterval` agora estão descontinuados e serão removidos na versão 0.75:

```js
type Notification = {
  ...
  // NEW: Seconds from now to display the notification.
  fireIntervalSeconds?: ?number,

  // CHANGED: Used only for scheduling notifications. Will be null when
  // retrieving notifications using `getScheduledLocalNotifications` or
  // `getDeliveredNotifications`.
  soundName?: ?string,

  // DEPRECATED: This was used for iOS's legacy UILocalNotification.
  alertAction?: ?string,

  // DEPRECATED: Use `fireDate` or `fireIntervalSeconds` instead.
  repeatInterval?: ?string,
};
```

Finalmente, o parâmetro `handler` no `PushNotificationIOS.removeEventListener` não é usado e foi removido.

<details>
<summary>**💡 Como Migrar**</summary>

#### iOS

Seu `AppDelegate` precisará implementar `UNUserNotificationCenterDelegate`. Isso deve ser feito na inicialização do aplicativo em `application:willFinishLaunchingWithOptions:` ou `application:didFinishLaunchingWithOptions:` (veja [Apple Docs](https://developer.apple.com/documentation/usernotifications/unusernotificationcenterdelegate?language=objc) para mais detalhes).

```objectivec
- (BOOL)application:(UIApplication *)application didFinishLaunchingWithOptions:(NSDictionary *)launchOptions
{
  ...
  UNUserNotificationCenter *center = [UNUserNotificationCenter currentNotificationCenter];
  center.delegate = self;

  return YES;
}
```

Implemente <code>[userNotificationCenter:willPresentNotification:withCompletionHandler:](https://developer.apple.com/documentation/usernotifications/unusernotificationcenterdelegate/1649518-usernotificationcenter?language=objc)</code>, que é chamado quando uma notificação chega e o aplicativo está em <em>primeiro plano</em>. Use o <code>completionHandler</code> para determinar se a notificação será mostrada ao usuário e notifique o <code>RCTPushNotificationManager</code> adequadamente:

```objectivec
- (void)userNotificationCenter:(UNUserNotificationCenter *)center
       willPresentNotification:(UNNotification *)notification
         withCompletionHandler:(void (^)(UNNotificationPresentationOptions options))completionHandler
{
  // This will trigger 'notification' and 'localNotification' events on PushNotificationIOS
  [RCTPushNotificationManager didReceiveNotification:notification];
  // Decide if and how the notification will be shown to the user
  completionHandler(UNNotificationPresentationOptionNone);
}
```

Para lidar quando uma notificação é tocada, implemente <code>[userNotificationCenter:didReceiveNotificationResponse:withCompletionHandler:](https://developer.apple.com/documentation/usernotifications/unusernotificationcenterdelegate/1649501-usernotificationcenter?language=objc)</code>. Observe que se você configurar notificações em primeiro plano para serem mostradas em <code>userNotificationCenter:willPresentNotification:withCompletionHandler:</code>, você deve notificar o <code>RCTPushNotificationManager</code> em apenas um desses callbacks.

Se a notificação tocada resultou no lançamento do aplicativo, chame `setInitialNotification:`. Se a notificação não foi previamente tratada por `userNotificationCenter:willPresentNotification:withCompletionHandler:`, chame `didReceiveNotification:` também:

```objectivec
- (void)  userNotificationCenter:(UNUserNotificationCenter *)center
  didReceiveNotificationResponse:(UNNotificationResponse *)response
           withCompletionHandler:(void (^)(void))completionHandler
{
  // This condition passes if the notification was tapped to launch the app
  if ([response.actionIdentifier isEqualToString:UNNotificationDefaultActionIdentifier]) {
  // Allow the notification to be retrieved on the JS side using getInitialNotification()
    [RCTPushNotificationManager setInitialNotification:response.notification];
  }
 // This will trigger 'notification' and 'localNotification' events on PushNotificationIOS
  [RCTPushNotificationManager didReceiveNotification:response.notification];
  completionHandler();
}
```

Finalmente, exclua os seguintes métodos e adapte a lógica nos callbacks acima que serão chamados em seu lugar:

1. <code>
     [application:didReceiveLocalNotification:](https://developer.apple.com/documentation/uikit/uiapplicationdelegate/1622930-application?language=objc)
   </code>
   [deprecated]
2. <code>
     [application:didReceiveRemoteNotification:](https://developer.apple.com/documentation/uikit/uiapplicationdelegate/1623117-application?language=objc)
   </code>
   [deprecated]
3. <code>
     [application:didReceiveRemoteNotification:fetchCompletionHandler:](https://developer.apple.com/documentation/uikit/uiapplicationdelegate/1623013-application?language=objc)
   </code>
   [não descontinuado, mas é substituído pelos métodos
   <code>UNUserNotificationCenterDelegate</code>]

Exclua quaisquer usos de <code>[application:didRegisterUserNotificationSettings:](https://developer.apple.com/documentation/uikit/uiapplicationdelegate/1623022-application?language=objc)</code> e o correspondente <code>didRegisterUserNotificationSettings:</code> do <code>RCTPushNotificationManager</code> também.

**Exemplo:** Veja o <code>[AppDelegate.mm](https://github.com/facebook/react-native/blob/main/packages/rn-tester/RNTester/AppDelegate.mm)</code> do RNTester.

#### JS

1. Remova quaisquer referências a `alertAction`.
2. Remova o argumento `handler` de quaisquer chamadas para `removeEventListener`.
3. Substitua quaisquer usos de `repeatInterval` disparando múltiplas notificações usando `fireDate` ou `fireIntervalSeconds` em vez disso.
4. Observe que `soundName` será null quando for acessado em uma `Notification` retornada de `getScheduledLocalNotifications()` e `getDeliveredNotifications()`.

</details>

### Remoção do Plugin React Native do Flipper {#removal-of-flipper-react-native-plugin}

O uso de [Flipper](https://fbflipper.com/) para inspecionar layouts do React Native, requisições de rede e [outros recursos de plugin do React Native](https://fbflipper.com/docs/features/react-native/), agora não é mais suportado. Na versão 0.74, removemos as bibliotecas nativas do Flipper e o código de configuração de novos projetos React Native. Isso significa menos dependências e configuração local mais rápida (veja [RFC original](https://github.com/react-native-community/discussions-and-proposals/blob/main/proposals/0641-decoupling-flipper-from-react-native-core.md)).

O diff para remover o Flipper do seu aplicativo pode ser visto no [Upgrade Helper](https://react-native-community.github.io/upgrade-helper/). Se você quiser preservar o Flipper em um aplicativo existente, ignore as linhas de diff relevantes.

<details>
<summary>**💡 Para reintegrar o Flipper**</summary>

O Flipper ainda pode ser usado como uma ferramenta autônoma para depurar um aplicativo Android ou iOS, e pode ser integrado manualmente seguindo a documentação do Flipper ([guia Android](https://fbflipper.com/docs/getting-started/android-native/), [guia iOS](https://fbflipper.com/docs/getting-started/ios-native/)).

Recomendamos que as equipes invistam em migrar para ferramentas de depuração nativas no Android Studio e Xcode.

</details>

### Outras Mudanças Incompatíveis {#other-breaking-changes}

**Geral**

- Fazer `start`/`end` em estilos sempre se referirem à direção de escrita ([#42251](https://github.com/facebook/react-native/pull/42251)).

**Android**

- Remoção de `JSIModule*` de `FabricUIManagerProvider` ([#42059](https://github.com/facebook/react-native/pull/42059)).
  - Esta API não estava sendo usada em código aberto — use [TurboModules](https://github.com/reactwg/react-native-new-architecture/blob/main/docs/turbo-modules.md) em vez disso.
- Descontinuar `UIManagerModule.showPopupMenu` e `UIManagerModule.dismissPopupMenu` ([#42441](https://github.com/facebook/react-native/pull/42441))
  - Esta API foi movida para o pacote npm [`@react-native/popup-menu-android`](https://www.npmjs.com/package/@react-native/popup-menu-android) e será removida na versão 0.75.

**iOS**

- Excluir argumentos `configFilename` e `configKey` da CLI de codegen do iOS ([#41533](https://github.com/facebook/react-native/pull/41533)).
- Mudar como [`bundleURL`](https://github.com/facebook/react-native/blob/0.74-stable/packages/react-native/template/ios/HelloWorld/AppDelegate.mm#L22-L29) é tratado ([#43994](https://github.com/facebook/react-native/pull/43994)).
  - Antes, `bundleURL` era definido quando o React Native era iniciado em uma variável de instância e não era possível atualizá-lo.
  - Agora, [`bundleUrl` é uma função](https://github.com/facebook/react-native/blob/0.74-stable/packages/react-native/template/ios/HelloWorld/AppDelegate.mm#L22-L29) que é reavaliada quando necessário, permitindo o uso de uma URL diferente entre atualizações.
  - Esta mudança afetará seu aplicativo apenas se você estava alterando a variável `bundleURL` após o aplicativo ser iniciado. Neste caso, mova a lógica que atualiza a variável para a [função `bundleURL`](https://github.com/facebook/react-native/blob/0.74-stable/packages/react-native/template/ios/HelloWorld/AppDelegate.mm#L22-L29) no `AppDelegate`.

Por favor, veja o [changelog completo](https://github.com/facebook/react-native/blob/main/CHANGELOG.md) para uma lista completa de mudanças incompatíveis.
